# STATE_CONTRACT - slice_24_observability_debuggability

## Session replay modes

- `disabled`: default. No frontend event ingestion.
- `local_only_ring_buffer`: frontend keeps recent redacted breadcrumbs in memory only for current session.
- `backend_persisted_events`: frontend batches redacted events to backend when enabled by env and auth.
- `logs_only`: backend structured logs only; no frontend ingestion.

Allowed MVP combination:

```txt
local_only_ring_buffer + backend_persisted_events
```

Only local and staging may use `backend_persisted_events` initially.

## Event lifecycle

```txt
captured -> redacted -> queued -> submitted -> accepted -> retained -> expired -> cleaned
```

Failure paths:

```txt
captured -> redacted -> rejected_local
submitted -> rejected_backend
submitted -> rate_limited
accepted -> cleanup_failed
```

Rejected events must not retry forever. Max retry window: current browser session.

## Session lifecycle

- `session_id` is generated by frontend per surface session.
- `session_id` resets on logout.
- `session_id` resets when surface changes.
- `session_id` must not be derived from Telegram ID, user ID, phone or token.
- Admin Web tabs may share `correlation_id` but each tab may have its own `session_id`.

## Operation lifecycle

- `operation_id` is generated per user action or backend critical operation.
- Critical operation examples: create order, report payment, confirm payment, create support ticket, staff permission mutation, Base USDC verification.
- Operation IDs are diagnostic only and never authorize actions.
