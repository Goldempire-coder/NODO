# API Contract

All routes use `/api/v1`, authenticated ownership checks, rate limits,
`X-Request-Id` and the canonical error envelope.

## PUT /api/v1/orders/{id}/receiver-details

Optional structured Pago Movil receiver details for an order.
The normal chat-first flow does not require this resource before delivery. If
used, it may render as a compact secure bubble, but it does not create a row in
`messages` and its values never appear in `messages.body`.

Headers:

```txt
Authorization: Bearer <session_jwt>
Idempotency-Key: required
```

Request:

```json
{
  "bank": "allowlisted bank code or normalized label",
  "phone": "+584121234567",
  "document": "V12345678",
  "holder": "Receiver name"
}
```

Response 200:

```json
{
  "data": {
    "order_id": "uuid",
    "status": "shared",
    "shared_at": "timestamp",
    "receiver_details_masked": {
      "bank": "Banco",
      "phone": "+58*******567",
      "document": "V***678",
      "holder": "N*** R***"
    }
  },
  "request_id": "req_..."
}
```

Rules:

- Actor is the active remitter owner.
- First creation requires `payment_confirmed`.
- Validate and normalize each field server-side; reject unknown extra fields:
  - `bank`: code from the backend-authoritative Pago Movil bank catalog;
  - `phone`: canonical `+58` followed by ten digits;
  - `document`: uppercase `V|E|J|G|P` plus 6..10 digits after removing allowed
    presentation separators;
  - `holder`: normalized whitespace, 2..120 characters, no control markup.
- The backend owns the order binding. The request cannot supply `order_id`,
  actor, visibility, status or recipient.
- Same key and canonical payload returns the same result.
- A different key with the same canonical payload returns the existing resource
  without duplicate audit or notification effects.
- Same key with different payload returns `IDEMPOTENCY_PAYLOAD_MISMATCH`.
- After the first accepted payload, receiver details are immutable for the
  order. A later different payload returns
  `ORDER_RECEIVER_DETAILS_ALREADY_SHARED`.
- Correction/replacement requires a future explicit protocol; it must not be
  improvised through chat or a second idempotency key.
- Store in a dedicated protected structure defined by the future runtime slice,
  not in chat, generic metadata, telemetry or audit payloads.
- Persist the protected resource and safe audit atomically; fail closed if the
  audit cannot be written.
- Enqueue one generic business notification without any receiver field.
- The business can still mark Pago Movil sent from `payment_confirmed` without
  this resource when the participants coordinated the receiver details in chat.
- Idempotency/resource lookup precedes the first-creation state guard:
  - an existing same-key/same-payload result replays in any later visible state;
  - an existing same canonical payload under another key returns the resource;
  - a changed payload after creation returns
    `ORDER_RECEIVER_DETAILS_ALREADY_SHARED`;
  - only a first creation evaluates the `payment_confirmed` requirement.

Errors:

- `ORDER_NOT_FOUND`
- `ORDER_NOT_OWNED`
- `ORDER_STATUS_INVALID`
- `ORDER_RECEIVER_DETAILS_INVALID`
- `ORDER_RECEIVER_DETAILS_ALREADY_SHARED`
- `IDEMPOTENCY_KEY_REQUIRED`
- `IDEMPOTENCY_PAYLOAD_MISMATCH`
- `RATE_LIMITED`

## GET /api/v1/orders/{id}/receiver-details

Explicit participant reveal for the active order workflow.

Rules:

- Only the remitter owner and business owner participants.
- Allowed while the order is `payment_confirmed`, `delivered` or `disputed`.
- Unrelated actors receive `ORDER_NOT_FOUND`.
- Response uses `Cache-Control: private, no-store`.
- Every full reveal audits actor, order ID, purpose and request ID without
  receiver values.
- Fail closed if the reveal audit cannot be persisted.
- Admin/support are forbidden from this participant endpoint.
- A future admin/support reveal requires a separate endpoint, explicit RBAC,
  reason and audit.
- If the order is eligible but no resource exists, return
  `404 ORDER_RECEIVER_DETAILS_NOT_FOUND`.

Response fields:

```json
{
  "data": {
    "order_id": "uuid",
    "bank": "Banco",
    "phone": "+584121234567",
    "document": "V12345678",
    "holder": "Receiver name",
    "shared_at": "timestamp"
  },
  "request_id": "req_..."
}
```

Errors:

- `UNAUTHENTICATED`
- `FORBIDDEN`
- `ORDER_NOT_FOUND`
- `ORDER_NOT_OWNED`
- `ORDER_STATUS_INVALID`
- `ORDER_RECEIVER_DETAILS_NOT_FOUND`
- `RATE_LIMITED`
- `INTERNAL_ERROR` when required reveal audit persistence fails

## POST /api/v1/orders/{id}/confirm-received

Official remitter confirmation that Pago Movil was received.

Headers:

```txt
Authorization: Bearer <session_jwt>
Idempotency-Key: required
X-Request-Id: required or generated by backend
```

Request body: empty.

Response 200:

```json
{
  "data": {
    "order": {
      "id": "uuid",
      "status": "completed",
      "completion_reason": "manual_confirmed",
      "completed_at": "timestamp"
    },
    "rating": {
      "can_rate": true,
      "already_rated": false
    }
  },
  "request_id": "req_..."
}
```

Rules:

- Actor is the active remitter owner.
- Required order state is `delivered`.
- No dispute for the order may be `open` or `in_review`.
- Lock order and dispute guard in the completion transaction.
- Transition `delivered -> completed` atomically.
- Set `completion_reason = manual_confirmed` and `completed_at`.
- Consume operational capacity exactly once.
- Do not consume publication credit; it was consumed at
  `payment_reported -> payment_confirmed`.
- Create one order state event and safe `order_completed` audit.
- Enqueue one generic business notification after the committed transition.
- Same key replay returns the same result without duplicate capacity, event,
  audit or notification effects.
- A non-idempotent replay observes terminal state and must not repeat effects.

Errors:

- `ORDER_NOT_FOUND`
- `ORDER_NOT_OWNED`
- `ORDER_RECEIPT_CONFIRMATION_NOT_ALLOWED`
- `ORDER_COMPLETION_BLOCKED_BY_DISPUTE`
- `ORDER_STATE_CONFLICT`
- `IDEMPOTENCY_KEY_REQUIRED`
- `IDEMPOTENCY_PAYLOAD_MISMATCH`
- `RATE_LIMITED`

## Auto-complete Contract

The operational runner is not activated by 50B0.

When a later slice activates it, the runner must:

- select `delivered` orders with `auto_complete_at <= now()`;
- skip any order with a dispute in `open|in_review`;
- call the same atomic completion use case as manual confirmation;
- use `completion_reason = auto_completed_after_24h`;
- consume operational capacity once and never consume publication credit again;
- enable rating when no dispute blocks rating under the rating contract;
- deduplicate 12-hour, 23-hour and completion notifications;
- use singleton locking, bounded batches, metrics and safe retry.

## Notification Rules

- `payment_confirmed`: tell the remitter to write Pago Movil in the chat.
- `order_receiver_details_shared_business`: tell the business to open the
  order; include no receiver field.
- `delivered_reminder_immediate|12h|23h`: tell the remitter to confirm receipt
  or open dispute; include no payment or receiver data.
- `order_completed`: tell the business that the remitter confirmed receipt.
- `order_auto_completed_after_24h`: tell both parties that the contracted
  timeout completed the order because no dispute blocked it.
- Every notification is deduplicated by order, type, recipient and applicable
  event/window.
- Telegram delivery failure follows the existing retry/permanent-failure
  contract and never rolls back the order transaction.

## Audit Rules

Required safe events:

- `order_receiver_details_shared`;
- `order_receiver_details_viewed`;
- `order_delivered`;
- `order_completed`;
- `business_capacity_consumed`;
- existing payment-confirmation, dispute and rating events.

Audit stores actor, order ID, transition, completion reason, safe result,
request/correlation/operation IDs and timestamps. It never stores receiver
values, chat bodies, payment instructions, evidence content, free metadata,
`account_value`, `storage_path` or signed URLs.
