# API_CONTRACT.md

Authoritative API contract for `slice_09_admin_console`.

Global API source:

- `control_plane/06_API_CONTRACTS/ADMIN_API.md`
- `control_plane/06_API_CONTRACTS/DISPUTES_API.md`
- `control_plane/06_API_CONTRACTS/ERROR_CONTRACT.md`

All active routes use `/api/v1`.

## Endpoints authorized for this slice

Read/admin console:

- GET /api/v1/admin/dashboard
- GET /api/v1/admin/businesses
- GET /api/v1/admin/businesses/{id}
- GET /api/v1/admin/orders
- GET /api/v1/admin/orders/{id}
- GET /api/v1/admin/disputes
- GET /api/v1/admin/disputes/{id}
- GET /api/v1/admin/audit-logs
- GET /api/v1/admin/metrics

Existing admin actions composed from previous slices:

- GET /api/v1/admin/businesses/pending
- POST /api/v1/admin/businesses/{id}/approve
- POST /api/v1/admin/businesses/{id}/reject
- GET /api/v1/admin/credit-purchases
- POST /api/v1/admin/credit-purchases/{id}/approve
- POST /api/v1/admin/credit-purchases/{id}/reject
- POST /api/v1/admin/credits/adjust

New slice 09 mutation:

- POST /api/v1/admin/disputes/{id}/resolve

Super-admin role management is in scope only if the builder implements the
contracted endpoint from `ADMIN_API.md`; otherwise it remains read-only display.

## Common headers

- `Authorization: Bearer <session_jwt>` required.
- `X-Request-Id` required or generated by backend.
- `Idempotency-Key` required for all mutating endpoints:
  - approve/reject business
  - approve/reject credit purchase
  - admin credit adjustment
  - resolve dispute
  - admin role change if implemented

## Common query rules

- Lists use cursor pagination.
- `limit` must be 1..50 unless a stricter endpoint contract says otherwise.
- Filters must be allowlisted per endpoint.
- Offset pagination is prohibited on hot tables.

## Masking and forbidden fields

Admin responses must not expose:

- `storage_path`
- raw secrets/tokens
- full payment instructions
- `account_value` unless a later explicit reveal endpoint permits it
- signed URLs outside short-lived authorized endpoints
- raw webhook payloads or Stripe secrets

Support responses are read-only and masked by default.

## POST /api/v1/admin/disputes/{id}/resolve

Request:

```json
{
  "resolution_type": "remitter_favored",
  "reason": "Evidence reviewed by admin",
  "notes": "Optional internal safe note"
}
```

Allowed `resolution_type`:

- `remitter_favored`
- `business_favored`
- `cancelled`
- `completed`
- `keep_under_review`

Rules:

- Requires active `admin` or `super_admin`.
- `support` is forbidden.
- Requires `Idempotency-Key`.
- Requires non-empty `reason`.
- Dispute must be `open` or `in_review`.
- Order must be `disputed`.
- Effects must follow `DISPUTE_RESOLUTION_MASTER.md`.
- Must create `dispute_events`.
- Must create audit event `dispute_resolved` for terminal resolutions.
- `keep_under_review` creates audit event `dispute_marked_in_review`.
- Must not move real money or claim NODO holds funds.

Response:

```json
{
  "data": {
    "dispute": {
      "id": "uuid",
      "status": "resolved",
      "resolution_type": "remitter_favored",
      "resolved_at": "timestamp"
    },
    "order": {
      "id": "uuid",
      "status": "cancelled",
      "public_order_code": "NODO-..."
    },
    "credit_effect": {
      "type": "consume",
      "amount": 2,
      "ledger_id": "uuid-or-null"
    },
    "ad": {
      "id": "uuid",
      "status": "archived"
    }
  },
  "request_id": "req_..."
}
```

Idempotency:

- Same key + same payload returns same result.
- Same key + different payload returns `IDEMPOTENCY_PAYLOAD_MISMATCH`.
- A resolved/cancelled dispute cannot be resolved again unless replaying the
  same idempotent result.

Errors:

- UNAUTHENTICATED
- FORBIDDEN
- DISPUTE_NOT_FOUND
- DISPUTE_STATUS_INVALID
- DISPUTE_RESOLUTION_NOT_ALLOWED
- DISPUTE_RESOLUTION_REASON_REQUIRED
- ORDER_STATUS_INVALID
- ADMIN_REASON_REQUIRED
- IDEMPOTENCY_KEY_REQUIRED
- IDEMPOTENCY_PAYLOAD_MISMATCH
- RATE_LIMITED
- VALIDATION_ERROR

## API rules

- Responses must follow `06_API_CONTRACTS/ERROR_CONTRACT.md`.
- Frontend cannot bypass backend permissions.
- Mutating endpoints require auth, RBAC, validation, reason, idempotency and audit.
- Sensitive read endpoints require RBAC, masking and rate limit.
